How to clear the WordPress cache in WordPress

Clearing the cache means deleting the stored HTML so the next request is rendered from scratch. In HarrierCache that is one button on the dashboard, but the reason a clear sometimes appears to do nothing is worth knowing: a page cache sits in front of PHP, so a cleared page is rebuilt on the next visit, and any CDN or proxy in front of the site keeps its own copy. Clearing twice in a row without a visit does not produce a different result.

Clearing one page instead of everything

A full purge is the safe habit during development and the wrong habit in production: every purge means the next visitor pays the render cost. HarrierCache purges the URL that changed when a post is edited, and the whole cache only when you press the button or change a setting that affects every page, such as minification.

When the cache should stay warm

On a shop, a purge during a sale is a self-inflicted slowdown: the first hundred visitors after a full purge all render. Configure purge-on-update for content pages, leave the product archive cached, and watch the hit rate on the dashboard for a day before deciding it is broken.

The three caches people confuse

If a change does not appear after clearing, check in that order: page cache, object cache, host cache. Most 'the plugin broke my site' reports end at step three.

WordPress has a page cache, an object cache and whatever your host put in front of the site. A page cache stores finished HTML. An object cache stores query results for reuse inside one request or across requests if a persistent backend exists. A host-level cache stores everything at the edge and is usually cleared from a hosting panel, not from WordPress. HarrierCache manages the first and exposes counters for both.

The honest test is a stopwatch, not a score. Load the same page five times with the plugin disabled and five times with it enabled, on the same network, and compare the median. Then check the cache page for a miss count that keeps rising on pages you never visit - that is usually a query string, a cookie, or a form that should have been excluded.

HarrierCache records what it did per request: whether it served from cache, how many bytes it saved, and how long generation took. Those three values are enough to tell a working setup from one that only looks configured.

Who this is for

The useful test: do you administer the site yourself, and does it run on hosting you can restart? If yes, HarrierCache is the whole performance stack. If someone else owns the platform and the CDN, the plugin is a smaller piece of a larger puzzle and the counters here will tell you how much of the problem was yours to begin with.

What it does not do

There is no account, no licence key, no tier that unlocks the useful half. Uninstalling it removes its options, its cache directory, its tables and its transients, because a plugin you cannot remove is a plugin you cannot evaluate honestly. Nothing here is gated behind an email address.

Frequently asked

Does clearing the cache delete my content?

No. It deletes generated HTML and stored counters. Posts, pages, media and settings are untouched; the next request regenerates the page.

Why is the site slower right after a purge?

Every cached page has to be rendered again. The first visitors after a purge pay that cost; the hit rate recovers as pages are visited.

Should I clear the cache after publishing a post?

HarrierCache purges the affected URL automatically on save, so a manual purge is only needed after changing a global setting.
